# requirements.lock.txt — 完整锁定的依赖清单（构建可复现，P2-2）
#
# 来源：从经过完整回归验证的开发 venv 直接 `pip freeze` 生成（含传递依赖与
# 开发工具 ruff/pytest）。刻意不用 pip-compile 解析最新版：requirements.txt
# 的 >= 约束会解析到未经验证的新版本（实例：flet 0.85.3 曾导致 GUI 无法启动，
# 本项目适配的是 0.85.2）。锁定文件记录"已知可用"，而非"最新可装"。
#
# 用途：
#   打包 / CI / 新环境搭建： pip install -r requirements.lock.txt
#   日常表达意图仍看 requirements.txt（宽松约束）
#
# 再生成（升级依赖后）：
#   1. 在 venv 中升级目标包并跑完整回归（pytest + 实际转换一次）
#   2. .venv/Scripts/python -m pip freeze > requirements.lock.txt（保留本头部）
#
# 注意：本锁定含 onnxruntime-gpu（NVIDIA/开发/CI 目标）。DirectML 分发目标
# 需要另一份锁定（onnxruntime-directml 替换 onnxruntime-gpu），在准备该
# 分发渠道时按同样流程从对应验证环境生成。
#
# 已剔除交叉分支污染（发现于依赖漏洞扫描审计）：开发 venv 同时装过
# exp/jianpu-vlm-ocr 分支手动安装的 llama-cpp-python（main 分支代码完全不
# import 它），首次 freeze 把它和它的专属依赖一并冻了进来——包括无后缀的
# CUDA 13 运行时包（llama-cpp-python 的 cu132 wheel 专用；main 分支的
# onnxruntime-gpu 用的是 nvidia-*-cu12 这套，与之无关，予以保留）。
# 已删除：llama_cpp_python, diskcache, Jinja2, MarkupSafe,
#         nvidia-cublas（无后缀）, nvidia-cuda-nvrtc（无后缀）,
#         nvidia-cuda-runtime（无后缀）。
#
# 2026-08-14 依赖巡检「清理批」（本文件与 requirements.lock.directml.txt 同步改动）：
#   移除 2 个死依赖——
#     musicxml==1.4    全仓库（含 omr_engine/homr 子模块）零 `import musicxml`，
#                      homr 自己的 pyproject.toml 也不依赖它；且 1.5~1.6.1 全部
#                      声明 requires_python "<3.13"，本项目跑 3.14 根本装不上。
#     pypdfium2==5.11.0 PDF 预览在 0.5.0 已移到前端 pdf.js，Python 侧零调用点。
#   小版本升级 14 个：anyio / certifi / cffi / chardet / charset-normalizer /
#     colorlog / omegaconf / packaging / pillow / protobuf / pypdf / ruff /
#     tqdm / typing_extensions。
#   验证：Input/image_test3.png 走 HOMR 端到端跑通，改动前后 .mid / .jianpu.txt /
#     .source.png 逐字节一致，PDF 字节数一致；归档 MusicXML 只差 music21 每次
#     运行随机生成的 <score-instrument id>（同环境连跑两次同样会变，与本次改动无关）。
#   （其中 anyio / pypdf 稍后又被下面的「PDF 库整理批」整个移除——升级时还没查到
#     它们其实无人使用。）
#
# 2026-08-14 依赖巡检「PDF 库整理批」（同样两份 lock 同步）：
#   PyMuPDF 1.27.2.3 → 1.28.2，并把代码里的 `import fitz` 全部改成 `import pymupdf`
#   （1.28 起 fitz 别名会在 stdout 上打弃用警告）。spec 的 collect_all 也从 'fitz'
#   改成 'pymupdf'——实测前者只收到 4 个 data、0 个 binary，后者才带上 mupdfcpp64.dll。
#
#   再移除 8 个无人使用的包：
#     pypdf            唯一调用点 _overlay_cjk_title_on_staff_pdf() 自 a88e012
#                      (2026-05-08，改用 LilyPond \markup 注入标题) 起就没有调用者，
#                      本次连函数一起删除。
#     httpx / httpcore / h11 / anyio / msgpack / oauthlib / repath
#                      全是 Flet 的传递依赖残留：Flet 在 0.5.0 被 pywebview 取代，
#                      但当时的 lock 是从仍装着 flet 的 venv `pip freeze` 出来的，
#                      于是它的下游被一并冻了进来。用「从一手 import 出发做可达性
#                      闭包」的方式扫出来的，本仓库任何地方都不 import 它们。
#   验证：卸掉这 8 个后，core/webui/gui 全部 50 个模块 import 无一失败；
#     `python -m webui.main --selftest` 全项通过（含 500 条事件洪泛门）；
#     pytest 46 passed；PDF 输入走 AUTO→Audiveris 端到端转换成功。
#
# 2026-08-15 v0.5.2 发版准备时发现本文件有一个**结构性盲区**：音频识别栈
#   （torch / librosa / numba / piano_transcription_inference 等）按 requirements.txt
#   的说明手工安装、**不在本锁定内**，所以任何"从我们自己 import 的包出发做
#   可达性分析"或"在没装音频栈的环境里 freeze"的做法，都看不见它的约束。
#   由此产生过三处错误，均已在本次修正：
#     msgpack==1.2.1   2026-08-14「PDF 库整理批」把它当作 Flet 遗留传递依赖删掉了。
#                      它同时也是 librosa 的硬依赖：删掉后 librosa.load /
#                      resample / beat_track 全部 ModuleNotFoundError，音频转简谱
#                      整条路径不可用。因为 librosa 用 lazy_loader 延迟导入，
#                      `import librosa` 仍然成功，故障要到真正转录时才爆。
#     numpy==2.4.6     此前钉 2.5.0，而 numba 0.66.0 硬要求 numpy<2.5
#                      （`import numba` 直接 ImportError）。在装了音频栈的机器上
#                      pip 会把 numpy 悄悄降级，锁定形同虚设。
#     setuptools==70.2.0  此前钉 82.0.1，torch 2.12.1 要求 setuptools<82。
#   教训：改动本文件后，除了在干净 venv 复现，还必须在**装了音频栈的** venv 里
#   跑一次 `pip check`——那是唯一能暴露这类冲突的地方。
